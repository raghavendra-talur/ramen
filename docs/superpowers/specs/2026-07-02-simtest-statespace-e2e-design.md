# simtest: a state-space e2e test framework for Ramen

Date: 2026-07-02
Status: Draft — pending review

## Problem

Ramen's correctness depends on a large state space: DRPC has 9 phases and ~27
progression values, VRG has its own replication states plus ~14 condition
types, and every transition waits on status written by an external actor
(csi-addons VolumeReplication, VolSync, Velero, OCM ManifestWork/
ManagedClusterView, S3, PVC binding, NetworkFence, ...). Existing test layers
each cover a slice:

- `internal/controller` envtest suite: real reconcilers, but external status
  is hand-patched per test — laborious, no systematic coverage.
- `e2e/`: real clusters and operators — high fidelity, but slow, happy-path
  only, no fault injection.
- mock mode (`internal/controller/mock/`, `ramen-mock`): fulfilling operators
  that satisfy the external control-plane contract — happy-path fidelity on
  real clusters, still minutes per scenario.

None can answer: *for each reachable state, what happens when each external
event arrives late, wrong, or never?*

## Goal

A new, self-contained e2e framework and test collection that systematically
exercises state × external-event combinations against the **unmodified ramen
binary**, fast enough to run hundreds of scenarios in CI.

**Hard constraint: no changes to any existing file.** The framework is a new
top-level directory `simtest/` with its own Go module (like `e2e/`). It uses
existing repo assets read-only: `bin/manager`, `config/crd/bases/`,
`hack/test/` CRDs, `config/dr-cluster/rbac/`, sample RamenConfigs.

## Approaches considered

1. **envtest world + simulated actors (chosen).** Three in-process envtest
   control planes (hub, dr1, dr2); the real ramen binary runs as subprocesses
   against them; the framework plays every external actor and can therefore
   inject any status, ordering, delay, or failure at any state. Milliseconds
   per event, full controllability, true black-box (tests `cmd/main.go`
   wiring too).
2. **On top of mock mode (drenv).** Highest fidelity (real OCM agents), but
   minutes per scenario, and fault injection is limited to fighting the mock
   fulfillers from outside. Combinatorial coverage impractical.
3. **Hybrid.** Approach 1 for the matrix plus a curated subset replayed on
   the mock-mode env as a fidelity anchor. Deferred: valuable, but two
   runners is scope creep for v1. The scenario API is designed so a
   drenv-backed `World` implementation can be added later.

## Architecture

```
simtest/
├── go.mod                  # own module; no edits to root go.mod
├── world/                  # bring-up: envtest clusters + ramen processes
├── actors/                 # simulated external systems (the event surface)
├── scenario/               # DSL: steps, gates, perturbations, assertions
├── invariants/             # always-on global safety checks
├── matrix/                 # state × fault combination generator
└── tests/                  # the test collection (T1–T4)
```

### world

Builds one "world" per test process (reused across scenarios; fresh world for
destructive scenarios):

- Three envtest control planes: `hub`, `dr1`, `dr2`. CRDs installed from
  `../config/crd/bases` and `../hack/test` (read-only paths into the repo).
- Kubeconfig files written per cluster to a temp dir.
- Ramen subprocesses launched from `../bin/manager`:
  - hub operator: `KUBECONFIG=hub.kubeconfig manager --config hub.yaml`
  - dr-cluster operator per managed cluster, same pattern.
  - RamenConfig files generated by the framework (leader election off,
    metrics off, `ramenControllerType` per role, S3 profiles pointing at the
    embedded S3).
- Embedded S3: gofakes3 (in-process) serving the profiles in both operators'
  configs.
- Bootstrap objects: ManagedClusters, DRClusters, DRPolicy, Placement +
  PlacementDecision, ramen operator namespaces, StorageClass /
  VolumeReplicationClass with `storageID`/`replicationID` labels (mirroring
  what `ramen-mock seed` creates).
- Process control: `Kill(cluster)`, `Restart(cluster)` — enables
  crash/recovery tests that no existing layer covers.

### actors

Each actor is a small controller loop inside the framework process, watching
one world cluster and writing the status a real external system would.
Reference behavior is ported (copied, not imported — `internal/` is not
importable across modules) from `internal/controller/mock/` fulfillers.

| Actor | Simulates | Contract fulfilled |
|---|---|---|
| ocmagent | work + view agents | applies ManifestWork manifests to the managed cluster, reports MW status; fulfills ManagedClusterView by reading the managed cluster |
| volrep | csi-addons | VolumeReplication / VolumeGroupReplication status, conditions, LastSyncTime |
| snapshotter | external-snapshotter | VolumeSnapshot / VolumeGroupSnapshot ReadyToUse + contents |
| pvbinder | kube-controller-manager + provisioner | binds PVCs, creates PVs (envtest has no KCM/scheduler) |
| volsync | VolSync | ReplicationSource sync times / LastManualSync; ReplicationDestination address + latestImage |
| velero | Velero | Backup/Restore Completed, BSL Available |
| fencer | csi-addons | NetworkFence Result=Succeeded |
| janitor | KCM garbage collector | ownerReference-based deletion (envtest has no GC) |

**Fault injection is an actor policy, settable per actor, per cluster, at any
point in a scenario:**

```go
type Policy interface{} // one of:
Normal{}                    // fulfill immediately
Silent{}                    // never respond (external system down)
Delayed{After: d}           // respond after d
FailWith{Condition/Status}  // respond with error/degraded status
DropNext{N: n}              // miss n events, then Normal
```

### scenario

Scenarios are Go code (no YAML DSL — YAGNI) built from four primitives:

```go
s := scenario.New(world)
s.Step(user.EnableProtection(app, drpolicy))        // user/API action
s.Gate(drpc.Progression(rmn.ProgressionCreatingMW)) // wait for observed state
s.Perturb(actors.Volrep.On(dr1), policy.Silent{})   // fault at this state
s.Step(user.Failover(drpc, dr2))
s.Expect(drpc.ParksIn(rmn.WaitForReadiness))        // assertion: safe holding state
s.Perturb(actors.Volrep.On(dr1), policy.Normal{})   // clear fault
s.Expect(drpc.Reaches(rmn.FailedOver, timeout))     // assertion: recovery
```

Gates observe DRPC/VRG status via watches; timeouts are short (seconds)
because actors respond in milliseconds.

### invariants

A continuous observer watches all three clusters in every scenario and fails
the test the moment a global safety property is violated, regardless of what
the scenario was asserting:

- **Single primary:** never two VRGs with `spec.replicationState: primary`
  for the same protected app on both clusters (outside of documented
  transitional windows, which are encoded explicitly).
- **Progression graph:** DRPC `status.progression` only moves along edges of
  a checked-in expected-transition table. New/unexpected edges fail loudly —
  this table doubles as living documentation of the state machine.
- **PeerReady honesty:** actions are only accepted when their documented
  preconditions (PeerReady, Available) held.
- **Final sync before relocate:** relocate never completes without
  `FinalSyncComplete` having been observed.
- **Cleanup completeness:** after Disable/Delete, no ramen-owned resources
  remain on either managed cluster.

The transition table is derived initially from observing happy-path runs plus
code reading; unknown-edge failures start as report-only, promoted to hard
failures once the table stabilizes.

### matrix

The core answer to "many states × many external events". A generator, not
hand-written tests:

1. Run the baseline scenario (e.g. failover) once; record the sequence of
   observed progression checkpoints.
2. For each checkpoint × each applicable actor fault, emit one scenario:
   reach the checkpoint, apply the fault, then assert:
   - the world parks without invariant violations (no wedge into an
     undocumented state), and
   - after clearing the fault, the action completes.
3. Each combination is an independent Go subtest
   (`TestMatrix/failover/at=CreatingMW/fault=volrep-silent`), parallelized,
   with the event log dumped on failure.

Expected scale for v1: ~3 baselines × ~10 checkpoints × ~6 faults ≈ 150–200
scenarios per run.

## Test collection (v1 scope)

- **T1 baselines:** enable protection, failover, relocate, disable, delete —
  Regional-DR, volrep, single Deployment workload (discovered-app style:
  framework creates the app resources directly; no ArgoCD/Subscription
  dependency).
- **T2 fault matrix:** generated as above, over the T1 baselines.
- **T3 ordering:** at gates with multiple pending external events (e.g. VRG
  status via MCV vs. VR status vs. S3 upload), deliver them in different
  orders.
- **T4 crash/recovery:** kill and restart the hub or dr-cluster operator at
  each checkpoint; assert reconciliation resumes and completes.

Deferred (v2+): VolSync flows, Metro-DR/fencing/MaintenanceMode, consistency
groups, recipes/hooks, randomized exploration with seeds and shrinking,
drenv-backed World for fidelity anchoring.

## Error handling & debuggability

- Every actor logs each fulfillment (cluster, CR, policy in effect) to a
  per-scenario event log; on failure the log plus a YAML dump of DRPC/VRG/MW/
  MCV across all clusters is written to the test artifacts dir.
- Flake policy: gates use watch-driven waits, not polling sleeps; timeouts
  scale from one knob so CI machines can widen them.

## Build & run

- `simtest/Makefile`: `make simtest` → ensures `bin/manager` is built
  (`make -C .. build`), ensures envtest assets
  (`hack/install-setup-envtest.sh`), runs `go test ./tests/...`.
- No changes to the root Makefile; CI wiring can be added later as a new
  workflow file.

## Risks

- **Contract fidelity:** actors might fulfill a contract more politely than
  real systems. Mitigations: port behavior from `internal/controller/mock/`
  fulfillers (kept in sync by review), and the deferred drenv anchor.
- **envtest gaps:** no KCM, scheduler, GC, or kubelet — covered by the
  pvbinder and janitor actors; any flow found to depend on other node-level
  behavior gets an explicit actor or is documented out of scope.
- **Ramen behavior discovered mid-build:** e.g. hub requiring cluster claims
  or addon CRs. Handled by adding bootstrap objects/actors; CRDs already
  exist in `hack/test/`.

## Success criteria

1. `make simtest` runs T1–T4 green from a clean checkout in under ~15 minutes
   locally, with zero modifications to existing files.
2. The fault matrix covers every progression checkpoint of the three
   baselines with at least silent/error/delayed faults per dependent actor.
3. At least the five global invariants above are enforced in every scenario.
4. A failing scenario reproduces deterministically from its subtest name.
